# Azure DevOps Intelligence Hub — Extension

A native Azure DevOps extension version of the dashboard: Repositories/Branches,
Pull Requests, Teams & Access, User Activity, Pipelines, and Work Items —
running **inside** Azure DevOps, using the logged-in user's own permissions.
No PAT, no CORS, nothing stored in the browser.

## Why this instead of the standalone HTML file

The original was a single HTML file calling `dev.azure.com` REST APIs directly
with `fetch()` from the browser. Azure DevOps does not send
`Access-Control-Allow-Origin` headers, so **every** call was blocked by the
browser's CORS policy before your PAT was ever checked. Running as an
extension solves this at the root: the SDK's REST clients route calls through
the Azure DevOps host frame (not a raw cross-origin `fetch()`), and
authentication is ambient — the extension runs as the signed-in user, no PAT
required.

## Building & deploying from GitHub

Yes — this repo includes `.github/workflows/publish.yml`, which does the
whole build → package → publish pipeline in CI. Nothing runtime needs to be
hosted by GitHub; the extension's files end up bundled *inside* the `.vsix`
and are served by Azure DevOps itself once installed. GitHub Actions' only
job here is: `npm ci` → `npm run build` → `tfx extension create` → (on a
version tag) `tfx extension publish`.

**One-time setup:**
1. Push this folder to a GitHub repo.
2. Generate a Marketplace PAT with **Marketplace (Publish)** scope from
   https://marketplace.visualstudio.com/manage (this is separate from any
   Azure DevOps org PAT — it authorizes publishing to your publisher
   account specifically).
3. In the GitHub repo: **Settings → Secrets and variables → Actions → New
   repository secret**, name it `AZDO_MARKETPLACE_PAT`, paste the token.

**Day to day:**
- Every push to `main` builds the extension and packages a `.vsix`, uploaded
  as a downloadable **build artifact** on the Actions run — useful for
  testing a build without publishing it.
- Pushing a tag like `v1.0.1` (`git tag v1.0.1 && git push --tags`) also
  **publishes** that build straight to the Marketplace under your publisher.
- You can also trigger a manual publish from the **Actions** tab via
  "Run workflow" with the `publish` checkbox ticked, without needing a tag.
- After a publish, go back to your org's **Organization Settings →
  Extensions → Shared** and click **Install** (or **Update**, on later
  versions) — publishing doesn't auto-install it into your org.

Remember to bump `"version"` in `vss-extension.json` before each tag —
Azure DevOps requires strictly increasing version numbers per publish.

## Folder structure

```
azdo-extension/
├── vss-extension.json      # Extension manifest (contribution + scopes)
├── package.json            # npm dependencies & build scripts
├── webpack.config.js       # Bundles src/main.js -> dist/main.bundle.js
├── img/
│   └── logo.png            # Extension icon (placeholder — replace freely)
├── src/
│   ├── index.html          # UI shell (Tailwind/Chart.js/xlsx via CDN)
│   └── main.js             # SDK init + all 5 data modules + rendering
└── dist/                   # Generated by `npm run build` — do not edit
```

## Prerequisites

1. **Node.js 18+** and npm (already checked into this environment).
2. **A Marketplace publisher account** — free, at
   https://marketplace.visualstudio.com/manage — this gives you a
   `publisher` ID to put in `vss-extension.json`.
3. **A Personal Access Token** with **Marketplace (Publish)** scope, used
   *once* to install the packaged extension to your org (not used by the app
   itself at runtime — this is only for `tfx` to upload the `.vsix`).

## Setup

```bash
cd azdo-extension
npm install
```

Edit `vss-extension.json` and replace:

```json
"publisher": "YOUR-PUBLISHER-ID",
```

with your actual publisher ID from step 2 above. Also feel free to swap out
`img/logo.png` for your own icon (128x128 PNG recommended).

## Build

```bash
npm run build
```

This runs webpack and produces `dist/index.html` + `dist/main.bundle.js`,
which is what the manifest's `uri` points at.

## Package into a .vsix

```bash
npx tfx-cli extension create --manifest-globs vss-extension.json
```

This produces something like
`your-publisher.azdo-intelligence-hub-1.0.0.vsix` in the project root.

## Install to your organization (privately — no public Marketplace needed)

1. Go to `https://marketplace.visualstudio.com/manage/publishers/<your-publisher-id>`.
2. **New extension → Azure DevOps** → upload the `.vsix`.
3. From the extension's page, click **Share** → add your organization
   (e.g. `https://dev.azure.com/yourorg`).
4. In your Azure DevOps org: **Organization Settings → Extensions**, find it
   under "Shared", and click **Install**.
5. Open any project — you'll see a new **"Intelligence Hub"** entry in the
   left-hand project navigation (hub group).

## Iterating during development

```bash
npm run watch          # rebuilds dist/ on file changes
npx tfx-cli extension create --manifest-globs vss-extension.json --rev-version
```

Re-upload the new `.vsix` version from the publisher portal each time (or
use `tfx extension publish` to do create+publish in one step once you've
configured a personal access token for `tfx login`).

## Known gaps / things to verify against your Azure DevOps version

- **`vso.graph` scope / Security Groups**: the "User Access" module currently
  lists **Teams and their members** via `CoreRestClient`. Full project
  Security Groups (Contributors / Readers / Project Administrators) require
  the Graph REST client (`azure-devops-extension-api` exposes this in newer
  versions as a `Graph` module) — not wired up here to keep the first version
  simple. If you need it, add:
  ```js
  import { GraphRestClient } from "azure-devops-extension-api/Graph";
  ```
  and follow the same descriptor-resolution pattern as the original HTML file.
- **`BuildRestClient.getBuilds()` signature**: this client method takes many
  positional parameters (queues, tags, result filters, etc.). The call in
  `main.js` passes only what's needed and `undefined` for the rest — this
  matches the common pattern in Microsoft's official samples, but if your
  installed `azure-devops-extension-api` version has a different parameter
  order, your editor's TypeScript definitions (even in a `.js` file, most
  editors will pick up the `.d.ts` hints from `node_modules`) will flag it —
  worth a quick check after `npm install`.
- **YAML-only pipelines**: `BuildRestClient.getDefinitions` /
  `getBuilds` cover both classic and YAML pipelines in modern Azure DevOps,
  so the separate "modern pipelines API" fallback from the original file
  was dropped as unnecessary — flag it if you find a pipeline type it misses.
- **Rate limits on large orgs**: the Repositories and User Activity modules
  fan out one request per branch / per repo respectively (same design as the
  original). For orgs with hundreds of repos or branches this can be slow —
  consider adding a concurrency cap (e.g. batches of 10, like the Pipelines
  module already does) if you hit throttling.

## Scopes requested (`vss-extension.json`)

| Scope | Why |
|---|---|
| `vso.code` | Repos, branches, commits, pull requests |
| `vso.build` | Pipeline definitions & build runs |
| `vso.work` | Work items (WIQL + details) |
| `vso.project` | Project/team metadata |
| `vso.identity` | Resolving display names/emails |
| `vso.graph` | Reserved for the Security Groups module if you extend it |

Trim scopes you don't need before publishing — Azure DevOps will prompt
whoever installs the extension to approve exactly this list.
